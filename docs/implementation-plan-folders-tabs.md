# MarkMello — план реализации: папки, вкладки и файловый сайдбар

## Статус

Черновик, готов к исполнению.

## Дата

2026-08-29

## Связанный ADR

[ADR-0007 — Folder workspace with document tabs](adr/adr_0007_folder_workspace_with_document_tabs.md), заменяет ADR-0006.

Источник дизайна: бандл `design/MD редактор_ файлы и папки.zip` — экраны 01–13 и его `README.md`.

## Цель

Открытая локальная папка с деревом файлов в левом сайдбаре и открытыми документами во вкладках, без деградации single-file fast path.

## Жёсткие правила реализации

1. Ничего из workspace-подсистемы не создаётся при старте с одним файлом. `WorkspaceViewModel` — только по команде «Открыть папку».
2. Никакого рекурсивного обхода, индексирования и предварительного парсинга. Дерево ленивое, поиск ограничен, watcher создаётся вместе с сессией папки.
3. Новых **цветов** в палитру не вводится; допускается один новый **ключ** на существующих значениях.
4. Только компилируемые биндинги (`x:DataType`) — publish идёт с `PublishAot`.
5. Каждый новый тип в настройках регистрируется в `MarkMelloJsonSerializerContext` в том же коммите, что и поле.
6. Новых пакетов не добавляется. `TreeDataGrid` не подключается.
7. `TabControl` не используется: он пересоздаёт контент и теряет позицию прокрутки `MarkdownDocumentView`.
8. Никакого `Process.Start` из Presentation — платформенные действия идут через `IPlatformServices`.

## M1 — Домен, открытие папки, сайдбар только для чтения

### Результаты

- Domain: `WorkspaceFolder`, `WorkspaceEntry` (`Path`, `Name`, `IsDirectory`, `IsSupportedDocument`), `OpenDocumentTab`, `WorkspaceSessionState`.
- Application: `IFilePicker.PickFolderAsync`, `IWorkspaceFileSystem.EnumerateChildren`, use cases `OpenFolderUseCase`, `ExpandFolderNodeUseCase`.
- Infrastructure: `Workspace/DirectoryWorkspaceFileSystem` на `Directory.EnumerateFileSystemEntries`; сортировка «каталоги, затем файлы», `StringComparer.OrdinalIgnoreCase`; пропуск `.git`, `node_modules`, `bin`, `obj` и скрытых элементов.
- Presentation: `WorkspaceViewModel`, `FileTreeNodeViewModel`, `Views/WorkspaceSidebarView.axaml` (`TreeView` + `HierarchicalDataTemplate x:DataType`), колонка сайдбара с `GridSplitter` в `MainWindow.axaml`.
- Entry points: пункт меню «Открыть папку», кнопка на welcome, `Ctrl Shift O`, drag&drop каталога.
- Команда «Закрыть папку» в меню приложения (на M1 просто закрывает сайдбар — вкладок ещё нет).
- Новый ключ кисти `MmTreeInertTextBrush` в обе `ThemeDictionaries`: light `#6F6A65`, dark `#A29E98`.
- Стили `Border.mm-sidebar`, `TreeViewItem.mm-tree-item` в `Themes/Controls.axaml`.

### Правила

- Сайдбар 260px по умолчанию, диапазон 220–340, ширина сохраняется в настройках (поле в `SettingsFileModel` плюс регистрация в json-контексте).
- Дерево показывает все файлы; поддерживаемые — цветом `MmTextBrush`, остальные — `MmTreeInertTextBrush` и инертны: клик выделяет строку, двойной клик не делает ничего, вкладка не открывается, сообщений нет.
- Раскрытие узла читает детей при первом раскрытии, повторное — из кэша сессии.
- При открытии папки открывается `README.md` из корня, если он есть; иначе пустое состояние.
- Клавиатурная навигация — штатная для `TreeView` (стрелки, `Enter`, `Home`/`End`, буквенный набор); специально ничего не отключаем.
- Ошибка чтения каталога показывается в узле, ошибка открытия файла — в document surface; окно продолжает работать.
- Плавающий гамбургер при открытой папке скрывается, его роль исполняет кнопка в шапке сайдбара (класс `Window.mm-workspace`).

### Готово когда

- Папка открывается всеми пятью способами, дерево раскрывается лениво, файл открывается в существующем viewer surface.
- Замеры single-file сценария не отличаются от M0 за пределами шума.
- Тест: `WorkspaceViewModel` не создаётся при старте с одним файлом.
- Тесты сортировки, пропуска служебных каталогов, классификации документ/не-документ.

## M2 — Вкладки

### Результаты

- `DocumentTabViewModel` — путь, заголовок, `IsDirty`, `BelongsToWorkspace`, `RenderedDocument`, ленивый `EditorSessionViewModel`, сохранённая позиция прокрутки.
- `OpenDocumentsViewModel` — `ObservableCollection<DocumentTabViewModel>`, `ActiveTab`, `VisibleTabs`, `OverflowTabs`, команды `Activate`, `Close`, `CloseOthers`.
- `ShellViewModel` — выделен из `MainWindowViewModel`: тема, оверлеи, настройки чтения, статус-бар, drag&drop, заголовок окна.
- Полоса вкладок: `ItemsControl` с горизонтальным `StackPanel` плюс один `ContentControl Content="{Binding ActiveTab.Content}"`; `Flyout` для «ещё N».
- Пустое состояние document surface (экран 07).
- Диалог dirty поднят с уровня окна на уровень вкладки.
- Стили `Border.mm-tab`, `Border.mm-tab-active` и новый стиль тултипа (фон `#1F1915`, текст `#FCFAF6`, JetBrains Mono 11px, радиус 5, паддинг `6px 9px`).

### Правила

- Ширина вкладки: минимум 120px, максимум 240px, по содержимому между ними; обрезка эллипсисом в конце.
- Тултип — путь относительно корня папки; для файлов вне папки — абсолютный.
- Одноимённые файлы: после имени добавляется имя родительской папки 11px `MmTextFaintBrush`, без скобок, только у конфликтующих вкладок, динамически. При конфликте и по родителю путь наращивается на уровень выше.
- Переполнение: срабатывает, когда сумма ширин вкладок плюс 60px под кнопку «ещё N» превышает доступную ширину; вытесняются вкладки с конца; активная всегда видима — попав в вытесняемые, меняется местами с последней видимой.
- Закрытие: крестик, `Ctrl W`, средний клик. Несохранённая вкладка показывает точку 6px `MmAccentBrush` вместо крестика; крестик возвращается под курсором.
- `Ctrl Tab` — по позиции слева-направо с закольцовкой, `Ctrl Shift Tab` — обратно. MRU не реализуем.
- Колесо мыши над полосой не делает ничего; перетаскивание вкладок не реализуем.
- Закрытие последней вкладки: в folder mode — пустое состояние, в single-file — welcome. Окно не закрывается.
- Полосы вкладок нет, когда вкладок ноль.
- Заголовок окна: `файл.md — папка — MarkMello`, с точкой после имени файла у несохранённого; в пустом состоянии — `папка — MarkMello`. На macOS суффикс `— MarkMello` не добавляется, заголовок центрирован.
- Каждая вкладка хранит и восстанавливает позицию прокрутки; `ContentControl` не должен пересоздавать `MarkdownDocumentView` при возврате на вкладку.

### Готово когда

- Открытие второго документа не теряет первый и его прокрутку.
- Переполнение и «ещё N» работают на ширине окна 1280 и меньше.
- Закрытие грязной вкладки поднимает существующий диалог.
- Тесты: активация, закрытие, закрытие грязной, состав `VisibleTabs`/`OverflowTabs` при переполнении, дизамбигуация одноимённых.
- Замеры single-file сценария не изменились относительно M0.

## M3 — Поиск, файловые операции, watcher

### Результаты

- `SearchWorkspaceFilesUseCase` плюс UI-состояния поиска (экран 11).
- `IWorkspaceFileSystem`: `CreateFile`, `CreateFolder`, `Rename`, `Duplicate`, `Delete`.
- Инлайн-редактирование строки дерева для создания и переименования (экран 09).
- Модальный диалог подтверждения удаления (экран 10) на паттерне существующего dirty-оверлея.
- Удаление в корзину ОС — см. отдельный раздел ниже.
- `ContextMenu` дерева: «Открыть в новой вкладке», «Переименовать» `F2`, «Дублировать», разделитель, «Показать в проводнике», «Удалить» `Del`.
- Расширение `IPlatformServices`: `RevealInFileManager(path)` и `MoveToTrashAsync(path)`.
- `FileSystemWorkspaceWatcher` и плашка «Файл изменён на диске».

### Правила

**Поиск.**

- Фильтрация по подстроке имени, без чтения содержимого; каталоги тоже попадают в выдачу и по клику раскрываются в дереве вместо открытия документа.
- Не-документы в выдачу не попадают.
- Лимиты: не более 200 совпадений в выдаче и не более 20 000 просмотренных записей, ограничение по глубине. При достижении лимита показывается плашка «Показаны первые 200 совпадений. Уточните запрос.», счётчик показывает `200+`.
- Индикатор процесса появляется только после 400 мс; до этого UI не меняется. Результаты дописываются по мере обхода, список не пересоздаётся.
- Каждое нажатие отменяет предыдущий запрос, `Esc` сбрасывает.

**Создание и переименование.**

- Инлайн, не диалог. Строка ввода встаёт туда, где элемент окажется после сортировки.
- Новый файл: расширение `.md` подставлено и приглушено, курсор перед ним; ввод другого расширения его заменяет.
- Куда вставляется: выделена папка → внутрь неё с раскрытием; выделен файл → в его папку; ничего не выделено → в корень.
- `Enter` создаёт: файл сразу открывается новой активной вкладкой, папка раскрывается пустой и остаётся выделенной. `Esc` и потеря фокуса — отмена. Пустое имя не создаёт ничего и не показывает ошибку.
- Недопустимые символы не блокируются при вводе — сообщение показывается под полем, `Enter` заблокирован, строка не закрывается.
- Переименование по `F2`: выделено имя без расширения, расширение доступно стрелкой вправо. Открытые вкладки этого файла обновляют заголовок.

**Дублирование.**

- `README.md` → `README copy.md` → `README copy 2.md` → `README copy 3.md`. Суффикс не локализуется.
- Копия попадает в ту же папку, выделяется в дереве, вкладка не открывается.

**Удаление.**

- Подтверждение обязательно. `Enter` и `Esc` — «Отмена»; «Удалить» требует явного выбора.
- Число элементов непустой папки считается на верхнем уровне, без рекурсии.
- Открытые вкладки удалённого файла (и файлов удалённой папки) закрываются.
- Ошибка показывается в той же карточке с кнопкой «Закрыть».

**Watcher.**

- `IncludeSubdirectories = true`, дебаунс 250 мс, диспетчеризация через `Dispatcher.UIThread.Post`. Создаётся вместе с сессией папки, уничтожается вместе с ней.
- Реакция открытых вкладок:

| Ситуация | Поведение |
|---|---|
| Содержимое изменено, вкладка чистая | Молча перезагрузить, сохранив позицию прокрутки |
| Содержимое изменено, вкладка грязная | Плашка «Файл изменён на диске» с «Перезагрузить» / «Оставить мои правки». Молча не перезагружаем никогда |
| Файл удалён, вкладка чистая | Вкладка закрывается; если была последней — пустое состояние |
| Файл удалён, вкладка грязная | Вкладка остаётся, в заголовке «(удалён)», `Ctrl S` пересоздаёт файл по тому же пути |
| Файл переименован снаружи | Вкладка следует за новым путём по паре событий `Renamed`; иначе трактуется как удаление |

- Сбой watcher деградирует до «дерево не обновляется автоматически», окно продолжает работать.

### Готово когда

- Все состояния экранов 09–11 воспроизведены.
- Удаление уходит в корзину на всех трёх платформах либо честно предупреждает о безвозвратности.
- Тесты: подсветка и отмена поиска, лимит выдачи, генерация имени копии, валидация имени, реакция вкладок на внешние события.
- Замеры: открытие папки, раскрытие узла, поиск по крупной директории.

## M4 — Сессия, второе окно, платформы

### Результаты

- Сохранение состояния окна: ширина сайдбара (глобально), состав вкладок, активная вкладка, раскрытые узлы (на окно).
- Второе окно для второй папки; фабрика окон и пересмотр DI.
- CLI: аргумент-каталог открывает папку.
- macOS и Linux: проверка раскладки, ярлыки `⌘`, платформенные значения «Показать в …».
- Тёмная тема проверена на живой сборке.

### Правила

- Холодный старт без аргументов не открывает последнюю папку. Автовосстановление запрещено (ADR-0007 Rule 10).
- Новое окно поверх текущего, тех же размеров, смещение `+32/+32`; каскад сбрасывается к позиции первого окна при выходе за рабочую область.
- Папка уже открыта в другом окне → новое окно не создаётся, существующее выходит на передний план. Сравнение путей нормализованное, на Windows без учёта регистра.
- «Открыть в новом окне» не выгружает папку из первого окна.
- `ShutdownMode = OnLastWindowClose`; закрытие окна с грязными вкладками проходит по ним последовательно, «Отмена» на любой отменяет закрытие.
- DI: `MainWindow` и `ShellViewModel` перестают быть синглтонами; `Func<TopLevel?>` перестаёт указывать на `lifetime.MainWindow` и резолвится от активного окна. Сервисы без состояния окна (тема, локализация, settings store, update service) остаются синглтонами.
- «Закрыть папку»: закрываются вкладки с `BelongsToWorkspace = true`; вкладки файлов, открытых поверх папки, остаются, окно переходит в single-file режим; если таких нет — welcome. Грязные проходят через диалог по очереди, «Отмена» отменяет всю операцию.

### Готово когда

- Две папки живут в двух окнах, настройки общие, вкладки раздельные.
- Повторное открытие уже открытой папки фокусирует существующее окно.
- Контрольные замеры совпадают с M0.

## Кроссплатформенное удаление в корзину

Управляемого кроссплатформенного API нет; `File.Delete` удаляет безвозвратно. Контракт — `IPlatformServices.MoveToTrashAsync(string path, CancellationToken)` с результатом `Trashed | Unsupported | Failed`.

| Платформа | Способ | Заметки |
|---|---|---|
| Windows | P/Invoke `SHFileOperationW` с `FOF_ALLOWUNDO`, либо COM `IFileOperation` | AOT-совместимо. `Microsoft.VisualBasic.FileIO.FileSystem` не используем: лишняя зависимость и худшая предсказуемость под trimming |
| macOS | `NSFileManager trashItemAtURL:` через `libobjc` (`objc_getClass` / `sel_registerName` / `objc_msgSend`) | Приложение и так линкует ObjC runtime; `osascript` не используем — он требует Automation-разрешения |
| Linux | `gio trash`, при отсутствии — freedesktop trash spec вручную (`~/.local/share/Trash/files` плюс `.trashinfo`) | Проверять, что путь на том же томе, что и корзина пользователя |

Правила:

- если корзина недоступна (сетевой путь, отключённая корзина, отсутствие каталога Trash), диалог удаления **меняет текст** на безвозвратное удаление и требует повторного подтверждения; молчаливого безвозвратного удаления быть не должно;
- реализация живёт в Infrastructure, Presentation зовёт только абстракцию;
- на этапе M3 достаточно Windows-реализации плюс корректный `Unsupported` на других платформах; macOS и Linux закрываются в M4.

## Локализация

Все новые ключи — в **оба** словаря `LocalizationService.cs`; формулировки — из таблицы «Локализация: английские строки» в `README.md` бандла.

1. **`TreeRevealInExplorer` — три ключа:** `TreeRevealInExplorerWindows`, `TreeRevealInExplorerMacOS`, `TreeRevealInExplorerLinux`; выбор в рантайме по `IPlatformServices.PlatformName`. Плоский словарь не умеет платформенные значения одного ключа.
2. **Множественные формы.** `ILocalizationService` умеет только `Format(key, args)`. Для подвала сайдбара («14 документов · 1 изменён») добавляется helper выбора формы: ключи вида `SidebarFooterDocumentsOne / Few / Many` и `SidebarFooterDirtyOne / Few / Many`, правило выбора — по языку (RU — три формы, EN — две). Альтернатива, если helper покажется избыточным: формулировка без согласования — «Документов: 14 · Изменено: 1» / «Documents: 14 · Unsaved: 1». Решение принимается в M1, до того как строка попадёт в оба словаря.
3. **Аргументы диалогов удаления** нумеруются единообразно: `{0}` — имя, `{1}` — количество элементов, во всех четырёх ключах, включая те, где используется только один из них.

## Риски

- **Регресс startup.** Любой workspace-код в конструкторе shell ломает главное требование. Проверка `IStartupMetrics` на каждом этапе, а не в конце.
- **Разделение `MainWindowViewModel`.** 1744 строки и 17 команд; делать отдельным коммитом без функциональных изменений, чтобы регресс был отличим от новой функциональности.
- **AOT.** Новые поля настроек без регистрации в source-gen контексте падают только в publish-сборке.
- **Корзина.** Три платформенные реализации через P/Invoke — самая непредсказуемая часть M3; при отставании допустимо выпустить M3 с Windows-реализацией и явным предупреждением на остальных.
- **Большие папки.** Без лимитов поиска и ленивого раскрытия UI встаёт; лимиты проверять на реальном `node_modules`.

### Два выхода за допуск — найдены и устранены

Обе регрессии сначала были зафиксированы как есть, затем привязаны к вехе бисектом (сборка M3 из worktree на коммите `97cf50d`) и закрыты.

**1. Раскрытие узла: 23.8 → 77.5 мс. Виноват M4.**

| Сборка | Раскрытие узла на `docs/` |
|---|---|
| M2 | 23.8 мс |
| M3 | 25.8 мс |
| M4 | 77.5 мс |
| M4 + фикс | **13.6 мс** |

Watcher оказался ни при чём. Причина — сохранение сессии: `JsonSettingsStore` пишет файл синхронно, а `PersistSessionAsync` звал его прямо из UI-потока на каждое изменение состава вкладок. Запись, вызванная открытием `README.md`, приходилась ровно на замер раскрытия. Правка (`e4dd3db`): запись коалесцируется паузой 400 мс и уходит в пул потоков.

**2. Память при старте: +8.8 МБ. Виноват M3.**

| Сборка | Рабочее множество, single-file |
|---|---|
| M2 | 201.8 МБ |
| M3 со стилями от M2 | 205.8 МБ |
| M3 как есть | 210.6 МБ |
| M4 + ленивые контролы | **199.4 МБ** |

A/B-сборка (M3, но `Themes/Controls.axaml` откачен к версии M2) показала, что 4.8 МБ из 8.8 давали новые глобальные стили, остальное — прочее содержимое M3.

При разборе вскрылось нарушение ADR-0007 Rule 3: сайдбар и полоса вкладок висели в визуальном дереве окна с запуска, просто скрытые. Правка (`580c698`): сайдбар, полоса вкладок, диалог удаления и плашка внешнего изменения переведены на тот же ленивый `ContentControl`-паттерн, который в приложении уже используется для оверлеев, а их стили вынесены из глобального словаря в сами контролы — `Controls.axaml` вернулся к дофичевым 938 строкам.

**Плата за это:** открытие папки стоит на 25 мс дороже, чем в M2 (128.8 против 100.7 мс) — работа переехала со старта на открытие папки. Это ровно тот размен, которого требует Rule 1: дешёвым обязан быть fast path, а не вторичный сценарий.

| Метрика | M2 | M4 итог |
|---|---|---|
| `ReadableDocument`, single-file | 472.2 | 479.5 |
| Рабочее множество, single-file | 202.4 | 199.4 |
| Открытие папки `docs/` | 100.7 | 128.8 |
| Раскрытие узла `docs/` | 23.8 | 10.3 |

Все четыре показателя в допуске: время старта в пределах шума, память ниже базовой, раскрытие узла быстрее прежнего, открытие папки дороже на осознанную величину.

### Находка по методике: сессия портит замер папки

M4 сохраняет состояние сессии, и повторный прогон на той же папке восстанавливает вкладки и раскрытые узлы — раскрытие становится бесплатным, а «открытие папки» перестаёт включать открытие `README.md`. Первый замер это и показал: `ExpandNode` 2.4 мс и `FirstWindow` 808 мс с минимумом 365 (бимодальность от параллельной сборки).

Правило: **folder-замеры делаются с очищенной сессией, по одному холодному прогону**. Скрипт для этого — `scratchpad/measure-folder-cold.ps1`; стоит перенести его в `tools/` рядом с `measure-startup.ps1`.

| Стадия | M1 | M2 |

| Рабочее множество, МБ | 206.7 | 205.1 |

Раскрытие узла подорожало вдвое — с 12 до 24 мс. Причина в том, что теперь при раскрытии перекладывается не только дерево, но и полоса вкладок в соседней колонке. Абсолютная величина остаётся незаметной для глаза, поэтому оптимизировать нечего; если в M3 с поиском и watcher цифра пойдёт дальше вверх — вот тогда смотреть.

### Решения, принятые по ходу

- **Переключение вкладки не перечитывает файл.** Вкладка держит снимок документа; тест со счётчиком обращений к загрузчику это фиксирует.
- **Позиция прокрутки уезжает во вкладку на каждое изменение**, а не спрашивается в момент переключения: к этому моменту вьюер уже показывает другой документ.
- **Восстановление прокрутки отложено до отрисовки.** До неё `ScrollBarMaximum` нулевой и любое смещение схлопывается в ноль.
- **`MainWindowViewModel` переименован в `ShellViewModel` отдельным механическим коммитом** после вкладок — так регресс переименования отличим от регресса фичи.

### Известная флакость

При одном из полных прогонов упал `MarkdownHeadingAnchorSluggerTests.DocumentViewRegistersDuplicateHeadingAnchorsWithStableNumericSuffix`, при повторных прогонах и в изоляции проходит. К вкладкам отношения не имеет — похоже на порядковую зависимость в headless-коллекции. Не чинилось; если повторится, разбирать отдельно.

### Как сравнивать этапы

Сравнивать по AOT-сборке — это то, что получает пользователь.

**Сравнение обязательно парное, в одной сессии.** Абсолютные пороги из отдельного прогона непереносимы: на M1 первый замер дал `ReadableDocument` 478 мс против 415 мс на M0, но контрольный перезамер **той же** M0-сборки следом показал 494 мс — разъехалась машина, а не код. Поэтому приёмка этапа выглядит так: собрать AOT предыдущего этапа и текущего, прогнать оба скриптом подряд, сравнить медианы. Расхождение в пределах ±10 % по времени и ±5 МБ по памяти — шум.

JIT-сборка нужна только для быстрой проверки между этапами: пересобирать AOT на каждый коммит дорого (около 6 минут), а относительная динамика в JIT видна и так.

### Замечания по методике

1. **Тайминги теперь печатаются и в Release.** Раньше `StopwatchStartupMetrics` писал их только под `DEBUG`. Печать снимка добавлена в smoke-режим (`MainWindow.WriteStartupTimings`), поэтому измеряется ровно та сборка, которая уезжает в релиз, и теми же командами, что и CI-прогон.
2. **`SecondaryFeatures` в сценарии чтения не отмечается.** `MarkSecondaryFeaturesReady()` вызывается только из оверлеев (тема, меню приложения, настройки), то есть в fast path не участвует. Для baseline стадия неприменима.
3. **`AppBootstrap` в AOT — ноль.** Между стартом процесса и первой отметкой нет ни JIT, ни загрузки сборок; разрешение `Stopwatch` здесь уже не важно.
4. **AOT-публикация на этой машине требует `vswhere.exe` в `PATH`** (`C:\Program Files (x86)\Microsoft Visual Studio\Installer`). Без него линковка ILCompiler падает с MSB3073. Команда публикации — из `.github/workflows/release-windows.yml`, вывод в `publish/m0-baseline-win-x64`.
5. **Мерить при незанятой машине.** Параллельная AOT-компиляция подняла медиану `ReadableDocument` в JIT-сборке с 2985 до 3428 мс — 15 % искажения, больше любого ожидаемого эффекта от фичи.
