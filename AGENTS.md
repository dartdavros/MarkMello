# AGENTS.md

Ресурсы к инструкциям лежат в папке `.agents`.

## Сообщения коммитов

Сообщения коммитов должны формироваться по правилам:

- `.agents/GitCommitMessages.md` — формат и правила написания commit message.
- `.agents/GitCommitEmoji.md` — таблица соответствия типов изменений и emoji.

Краткий формат:

`:emoji: type(scope)!: short description`

Пример:

`:sparkles: feat(api)!: send an email to the customer when a product is shipped`

Достоверность локальной проверки / запрет на подмену окружения:
- Никогда без отдельного явного разрешения владельца не создавать и не запускать mock API, fake backend, временные HTTP-серверы, fixtures, seed-данные или другие заглушки, чтобы показать результат работы или обойти отсутствие штатного окружения.
- Нельзя выдавать интерфейс, работающий поверх заглушек или неполного набора API-ответов, за нормально запущенный локальный проект либо за пройденную проверку. Это недопустимое введение владельца в заблуждение.
- Для локальной проверки использовать только штатный контур проекта: его реальный backend, compose/dev-скрипты и предусмотренные документацией сервисы. Если этот контур недоступен, остановиться, честно сообщить blocker и запросить указание владельца; не подменять его самостоятельно.
- Это правило действует для любого проекта, включая временные файлы и процессы вне репозитория.

UI / дизайн:
- Никакой отсебятины в UI: не добавлять экраны, блоки, карточки, иконки, тексты, анимации, цвета, layout-решения и состояния, которых нет в утвержденной документации или design baseline.
- Если UI-этап еще не наступил, UI не считается реализованным и не должен маскироваться под готовый продуктовый интерфейс.
- Когда наступает UI-этап, реализация должна на 100% опираться на утвержденный baseline/design-файлы: структура, иерархия, визуальный язык, терминология, компоненты и состояния сохраняются.
- Отсутствие дизайна или состояния является blocker/design gate. Не придумывать самостоятельно, остановиться и явно сообщить, что требуется дизайн/решение владельца.
- Не упрощать UI, анимации, иконки, состояния или поведение по своему усмотрению. Любое отклонение от baseline требует явного согласования до правок.
- Технические временные заглушки UI не считать готовой реализацией и не использовать как основу продуктового UI без отдельного явного разрешения.

Engineering rules / обязательные практики:
- Соблюдать DRY, KISS, SRP, separation of concerns и NO GOD FILES.
- Не реализовывать полноценную страницу, feature или крупный workflow одним большим компонентом/файлом.
- Если компонент превышает примерно 180 строк или смешивает layout, state, data/model и subviews, разделить его до завершения задачи.
- Если новый или измененный файл превышает примерно 300 строк из-за текущей работы, остановиться и вынести части в меньшие модули до финального ответа или коммита.
- Page-компоненты должны быть преимущественно composition-only: subviews выносить в соседние компоненты, демо/static data в model/data файл, повторяемый UI в shared/local reusable components.
- Не инлайнить сложный UI повторно. Выносить компонент, если структура повторяется или секция имеет отдельную ответственность.
- Если реализация по задаче конфликтует с этими правилами, остановиться и явно сообщить blocker вместо поставки плохой структуры.

Definition of Done:
- При мелких локальных правках (например, CSS, размеры шрифта, цвета, отступы, простая перестановка элементов или текстов) не запускать сборку автоматически. Сборка для таких правок — только по прямому указанию владельца; завершение задачи или коммит сами по себе не являются основанием для сборки.
- Для остальных изменений кода перед ответом "готово" или перед коммитом должна пройти сборка и только тесты, покрывающие изменённый код и непосредственно затронутые сценарии. Полный прогон — только перед релизом или по прямому указанию владельца.
- Для UI-изменений должна быть выполнена browser-проверка.
- Измененные файлы должны быть проверены на NO GOD violations.
- Новый компонент не должен владеть несвязанными ответственностями.
- Не должно быть придуманных текстов, иконок, layout-решений или состояний вне design/docs.
- Любое отклонение от design/docs должно быть явно указано.

МАКЕТ — ЗАКОН:
- ОТХОДИТЬ ОТ МАКЕТА — ТОЛЬКО ПРИ ПРЯМОМ УКАЗАНИИ ВЛАДЕЛЬЦА НА ЭТО. Экраны, списки, блоки, тексты, порядок, состояния — ровно как в макете; «упростил/сделал по-своему» = невыполненная работа. Сомневаешься — спроси, не отходи.

## Тесты и объём проверок (правило владельца)

- Писать только тесты, необходимые для покрытия значимого поведения и требований задачи. Не добавлять малозначимые тесты или тесты ради количества.
- После изменений в коде запускать только тесты, покрывающие изменённый код и непосредственно затронутые сценарии.
- Полный прогон тестов выполнять только перед релизом или по прямому указанию владельца. Завершение задачи, коммит, обычная сборка и создание локального проверочного пакета сами по себе не являются основанием для полного прогона.
